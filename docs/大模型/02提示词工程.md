# 提示词工程：把任务接口定义清楚

“提示词工程”这个词被说得太神秘了。  
真正做项目之后会发现，Prompt 最核心的工作其实很朴素：

> 把模型该做的事说清楚，把模型不该做的事限制住。

如果把这个问题想清楚，很多所谓“调 Prompt 的技巧”，其实都只是接口设计。

## Prompt 为什么重要

很多输出不稳定的问题，看起来像“模型不够聪明”，本质上却是任务没有定义清楚。  
例如下面这些信息如果没写明，模型就很容易偏：

- 它到底要解决什么任务
- 需要基于哪些材料回答
- 输出形式应该是什么
- 哪些内容不能编

Prompt 的价值，不在于制造花哨话术，而在于减少任务歧义。

## 一个好 Prompt 至少要回答 4 个问题

### 1. 角色是什么

模型要扮演什么身份，决定了它的回答风格和重点。  
比如“技术顾问”和“客服助手”，哪怕面对同一个问题，也应该有不同输出方式。

### 2. 任务是什么

Prompt 里最忌讳“看起来有要求，其实要求不具体”。  
“请优化一下”通常不够，应该写成更可执行的任务，例如：

- 请总结成 3 点
- 请按表格输出
- 请只保留结论，不展开背景

### 3. 上下文是什么

如果回答必须依赖材料，就要明确告诉模型：

- 哪些文本是证据
- 哪些是用户补充信息
- 哪些内容不能超出材料去发挥

### 4. 输出标准是什么

很多项目里，真正决定可用性的不是“答得像不像人”，而是“输出能不能直接接下游系统”。  
所以经常要明确：

- 输出格式
- 字段顺序
- 是否需要 JSON
- 是否需要引用来源

## 最小可用 Prompt 模板

下面这类模板，往往比“灵感式提问”稳定得多：

```text
你是一名 AI 应用开发顾问。

任务：
请根据给定材料，总结这项技术在企业项目中的作用、适用场景和常见误区。

要求：
1. 只基于材料回答
2. 输出 3 个小节：作用、适用场景、常见误区
3. 不要编造材料中没有的信息

材料：
{{context}}
```

这个模板的本质，不是“更高级”，而是信息边界更清楚。

## Prompt 能解决什么，不能解决什么

Prompt 很适合解决这些问题：

- 让输出更稳定
- 让格式更统一
- 让模型少跑题
- 让任务目标更明确

但它不适合独自解决这些问题：

- 模型根本不知道的外部知识
- 私有文档问答
- 长链路决策错误
- 持续风格一致但样本又很复杂的任务

遇到这些问题时，往往就该考虑：

- RAG
- 工具调用
- 工作流拆分
- 微调

## 企业里最常见的 3 类 Prompt 场景

### 1. 信息提取

目标是从长文本里抽取结构化字段。  
这类场景重点不是文采，而是字段定义和格式约束。

### 2. 内容生成

目标是写摘要、写说明、写回复。  
这类场景重点是角色、风格和输出长度。

### 3. 推理与决策辅助

目标是让模型帮忙分类、判断、比较方案。  
这类场景重点是判断标准是否明确，证据是否充分。

## 常见误区

- 把 Prompt 当成万能调参器
- 只堆很多要求，却没有任务主线
- 没有输出格式约束
- 没说明“只能基于材料回答”
- 把应该拆成多步的任务硬塞进一个 Prompt

## 更务实的判断

如果一个问题通过“把任务说清楚”就能明显改善，那先别急着上更重的方案。  
但如果已经把任务边界写清楚，模型还是老出错，那问题多半不再是 Prompt 本身，而是知识、流程或系统设计出了问题。
