# 语义搜索与 RAG：真正影响效果的是整条检索链

RAG 现在几乎成了做大模型应用的默认配置。  
但很多项目做了一圈之后发现，问题并不在“有没有接向量库”，而在：

> 检索链是不是足够稳。

如果把 RAG 理解成“把文档扔进向量库，然后问模型问题”，那效果很容易上不去。  
因为真正决定质量的，从来不是某一个点，而是前后整条链。

## RAG 先解决什么问题

大模型天然有三个短板：

- 知识会过时
- 容易一本正经地胡说
- 不知道企业内部私有资料

RAG 的价值，不是把模型变聪明，而是把外部证据接进回答过程。  
换句话说，它是在给模型补“证据链”，不是单纯补“记忆”。

## 一条完整的 RAG 链路，至少有 5 个环节

### 1. 文档清洗

如果文档本身脏、乱、重复，再强的模型也很难救回来。  
很多项目的根问题，其实出在数据预处理，而不是出在模型。

### 2. 文档切分

切得太大，主题混杂；切得太小，上下文断裂。  
Chunk 策略直接影响后续召回质量，是很多团队最容易低估的一步。

### 3. 表示与索引

Embedding 模型决定“文本怎么被表示”，向量库决定“这些向量怎么被存和找”。  
这里常见的误判是：把模型表示问题误看成数据库问题。

### 4. 召回

召回阶段的核心目标不是最终排序最优，而是尽量把相关候选先找回来。  
它更偏覆盖率，而不是最终精度。

### 5. 精排与生成

Reranker 负责进一步优化相关性，Prompt 负责组织上下文并约束模型输出。  
如果没有这一步，系统常常会出现“找到了一堆差不多的内容，但模型还是答得不稳”。

## 为什么很多 RAG 项目效果不好

最常见的原因往往不是“模型不够大”，而是：

- 文档清洗没做好
- Chunk 粒度不合理
- 只做向量检索，不做关键词补充
- 没有 Reranker
- Prompt 没有要求“只基于证据回答”

也就是说，很多团队觉得自己在做 RAG，实际只是“给模型前面加了个向量库”。

## 一个更实用的理解：RAG 不是单点技术，而是系统工程

更完整的表达应该是：

> RAG = 数据准备 + 表示 + 检索 + 精排 + 生成约束

一旦这样看，问题就更容易诊断了。  
效果不好时，团队不再只会说“再换个模型试试”，而是能判断：

- 是文档问题
- 是切分问题
- 是召回问题
- 是排序问题
- 还是生成约束问题

## 企业里更常见的默认方案

如果目标是先做一个靠谱版本，通常更稳妥的起步策略是：

1. 先把文档清洗好
2. 选一个合理的 Chunk 策略
3. 向量检索和关键词检索结合
4. 加入 Reranker
5. 在 Prompt 里要求“只基于证据回答”
6. 输出引用来源

这套方案不一定最炫，但通常比单纯堆模型更有效。

## 常见误区

- 把 RAG 理解成“接个向量库就结束”
- 只关注 Embedding 模型，不关注数据清洗
- 不区分召回和精排的职责
- 没有评估集，只靠主观试问
- 出了问题只想换模型，不拆链路

## 最后

RAG 真正难的，不是“会不会接向量库”，而是：

- 有没有把检索链拆清楚
- 能不能找到真正影响效果的环节
- 是否建立了可以持续迭代的评估方法

把它当成单点能力，就容易陷入调参泥潭。  
把它当成系统工程，很多问题反而会变得可诊断、可优化。
