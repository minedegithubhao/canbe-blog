# 大模型应用开发的起点

很多人一开始学大模型，最容易掉进一个坑：  
名词记了不少，真正做项目时却不知道这些名词和代码、接口、成本、效果到底有什么关系。

这篇文章不追求把概念讲得“百科全书式完整”，而是只做一件事：

> 把大模型应用开发里最基础、也最常反复碰到的几个概念，放回工程语境里重新理解。

## 1. Token 不是“一个字”

初学者最常见的误解，是把 token 直接等同于“一个汉字”或者“一个单词”。  
更稳妥的理解是：

- token 是模型处理文本时使用的最小离散单位
- 它可能是一个字、半个词、一个词，甚至一个符号
- 模型的输入、输出、成本和上下文限制，最后都会落到 token 上

所以 token 重要，不是因为它是概念题，而是因为它直接决定：

- 一次请求能塞多少内容
- 请求大概会花多少钱
- 长文本场景会不会被截断

## 2. 分词器和词表，决定了模型怎么“看文字”

模型并不是直接看汉字和英文句子，它先要经过分词器，把自然语言切成 token，再映射成 ID。  
所以：

- 分词器决定“怎么切”
- 词表决定“模型认识哪些 token”

这就像把自然语言先翻译成模型内部能处理的编码系统。  
如果不了解这一步，很多上下文长度、截断、特殊符号行为的问题都很难解释。

## 3. 上下文窗口，决定了模型一次能记住多少东西

上下文窗口本质上就是模型一次推理时能处理的 token 上限。  
它影响的不只是“能不能放下整篇文档”，更影响：

- 多轮对话是否容易遗忘前文
- RAG 拼进去的材料能否完整保留
- 提示词是否需要更克制地组织信息

很多时候，问题不是模型不会答，而是上下文已经超了，或者关键证据被挤掉了。

## 4. Embedding 不负责回答问题，它负责表示文本

Embedding 经常被初学者误解成“另一个大模型回答器”，其实它做的事情更基础：

- 把文本映射成向量
- 让系统可以按“语义相近”而不是“字面相同”去找内容

所以在系统里，它更像“检索前的表示层”。  
如果要做 RAG、相似问答、语义搜索，Embedding 通常是前置能力，而不是最终输出能力。

## 5. Prompt 的本质，是任务接口

Prompt 不是给模型“施法”，而是在定义任务接口。  
它需要回答的问题通常包括：

- 你要模型做什么
- 你给了它哪些上下文
- 你希望它输出成什么格式
- 哪些内容不能乱写

如果任务接口定义得模糊，模型再强，输出也容易飘。

## 6. 成本、延迟、效果，永远要一起看

很多人做大模型应用时，一开始只盯着效果。  
但工程上真正要同时平衡的，往往是三件事：

- 效果够不够好
- 延迟能不能接受
- 成本能不能长期承担

这三者的关系很像产品里的“铁三角”。  
一个只追求效果、不看成本和响应时间的方案，很难真正上线。

## 一个更完整的系统视角

如果把大模型应用开发压缩成一条最小链路，大致可以这样理解：

1. 用户输入自然语言
2. 分词器把文本切成 token
3. 模型在上下文窗口内做推理
4. 如果需要外部知识，就走检索或工具调用
5. 最终再把输出 token 还原成人能读的结果

一旦这样看，很多概念就不再是散点，而是系统链路里的不同位置。

## 初学者最容易踩的坑

- 把 token 当成死板的“字数换算器”
- 只记上下文窗口大小，不理解它对真实任务的影响
- 把 Embedding 和生成模型混为一谈
- 觉得 Prompt 只是“措辞技巧”，而不是任务定义
- 只关注模型分数，不关注成本和延迟

## 学完这一篇之后，最应该建立的判断

他不一定要立刻背出所有术语定义，但至少应该开始形成这种意识：

> 大模型应用开发不是“直接把问题丢给模型”，而是围绕 token、上下文、表示、检索和输出设计一整条链路。

这才是后面学习 Prompt、RAG、Agent、微调时真正的起点。
