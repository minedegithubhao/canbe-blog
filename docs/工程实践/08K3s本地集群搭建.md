# K3s 本地集群搭建

很多人学 Kubernetes，最先卡住的不是概念，而是环境。

比如：

- 想本地起一个三节点集群
- 不想直接上云
- 想保留尽量接近真实服务器的体验

这时候，`Vagrant + K3s` 是一条很适合学习和实验的路线。

K3s 可以先这样理解：

**它是一个更轻量的 Kubernetes 发行版，特别适合本地实验、小型环境和边缘场景。**

## 这套环境怎么搭

这里的路线很清楚：

1. 先用 Vagrant 起 3 台虚拟机
2. 一台做 `master`
3. 两台做 `node`
4. 先装 server，再让 agent 加入集群

这条路线比一上来就折腾完整 Kubernetes 发行版要轻很多。

## 三台机器的基础规划

这里这组 IP 可以直接沿用：

- `k8s-master`：`192.168.56.10`
- `k8s-node1`：`192.168.56.11`
- `k8s-node2`：`192.168.56.12`

这种固定 IP 的价值很大，后面做节点加入、服务互通、排错都更省事。

## 起虚拟机前，先把旧环境清掉

如果之前已经乱试过一轮，先清环境：

```bash
vagrant destroy -f
```

这一步很重要。集群实验环境一旦乱了，硬修通常比重建更费劲。

## 先让 Vagrant 把三台虚拟机起起来

这里给的是多节点 `Vagrantfile`，核心结构就是：

```ruby
Vagrant.configure("2") do |config|
  config.vm.box = "centos/stream9"

  nodes = {
    "k8s-master" => { :ip => "192.168.56.10", :cpus => 2, :mem => 4096 },
    "k8s-node1"  => { :ip => "192.168.56.11", :cpus => 2, :mem => 4096 },
    "k8s-node2"  => { :ip => "192.168.56.12", :cpus => 2, :mem => 4096 }
  }
end
```

起完之后，先确认机器状态：

```bash
vagrant status
```

## 先装 Master，再拿 Token

这里最关键的一步不是命令本身，而是顺序。

顺序必须是：

1. 先进入 `k8s-master`
2. 启动 K3s server
3. 拿到 token
4. 让两个 node 加入

进入 master：

```bash
vagrant ssh k8s-master
```

安装完 server 之后，最关键的是拿 token。这里已经明确强调：

> Token 相当于加入集群的密码。

## Node 加入集群时，最容易错的是 IP 和 Token

这里特别提醒了两点：

- `node1` 的 `--node-ip` 是 `.11`
- `node2` 的 `--node-ip` 是 `.12`

这种地方一旦写错，现象通常不是“命令直接报错”，而是节点怎么都起不正常，排查起来很烦。

所以这里一定要做两次确认：

- Token 是不是 master 当前生成的
- IP 是不是和当前节点对应

## SELinux 是这类实验环境的高频坑

这里反复提到一类报错：

```text
Job for k3s-agent.service failed because the control process exited with error code.
See "systemctl status k3s-agent.service" and "journalctl -xeu k3s-agent.service" for details.
```

这类问题里，SELinux 是高频元凶之一。

排查思路一般是：

1. 修改配置
2. 关闭或放宽 SELinux
3. 再重启服务

也就是说，不要看到 agent 起不来，就马上怀疑 K3s 本体，先看系统层限制。

## `kubectl: command not found` 也很常见

这里还有一个很实战的坑：

```text
sudo: kubectl: command not found
```

这个问题的本质往往不是没装，而是：

- 路径没加进环境变量
- `sudo` 的 PATH 不认当前配置

更稳的排查顺序是：

1. 先定位 K3s 自带的 `kubectl` 路径
2. 用绝对路径验证一次
3. 再补环境变量
4. 需要的话再让 `sudo` 也能认这条路径

这比直接反复重装要有效得多。

## 最后怎么验证集群起好了

最终还是要回到最基本的检查：

```bash
sudo kubectl get nodes
```

如果三台节点都正常出来，说明这套本地 K3s 集群已经基本跑稳了。

## 最后

这套环境最难的地方，不是命令本身，而是：

- 多节点顺序别乱
- Token 和 IP 别配错
- SELinux 和 PATH 这类系统问题要优先排

把这些坑提前知道，本地 K3s 集群就不会搭得那么痛苦。
