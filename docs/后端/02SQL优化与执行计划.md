# SQL 优化与执行计划：连同 Redis、Docker 和微服务排障一起看

这里这一篇其实不是单纯的 SQL 笔记，而更像一份后端面试和实战复盘清单。  
里面最有价值的地方，不是知识点多，而是它把几个高频问题放在了同一个视角下：

- 数据库查询为什么慢
- Redis 为什么快、缓存为什么会出问题
- Docker 容器为什么会 OOM
- 微服务为什么会雪崩

所以这篇文章不再只讲 SQL，而是把这些性能与架构高频点放在一起梳理。

## 一、SQL 优化的入口，永远是执行计划

真正靠谱的顺序应该是：

1. 先看 `EXPLAIN`
2. 看访问类型
3. 看预估扫描行数
4. 看排序和临时表
5. 再决定要不要改索引、改 SQL 或改表结构

### 1. `type` 是最重要的字段

- `system` / `const`：通常很优
- `eq_ref`：多表连接里不错
- `ref`：常见可接受
- `range`：范围扫描，很多业务场景都正常
- `index`：全索引扫描，已经要警惕
- `ALL`：全表扫描，最差情况

> 大表里一旦出现 `ALL` 或 `index`，通常就应该起疑。

### 2. `possible_keys` 和 `key` 要一起看

- `possible_keys`：理论上可能使用的索引
- `key`：实际上真正使用的索引

如果 `possible_keys` 有值，但 `key` 是 `NULL`，往往说明：

- 索引不是没有
- 只是优化器认为不值得用

### 3. `rows` 和 `Extra` 是最直观的告警区

`rows` 代表预估扫描行数。  
如果最终只返回 20 行，但预估要扫 20 万行，这条 SQL 八成不健康。

`Extra` 则重点盯下面几个：

- `Using index`
- `Using where`
- `Using filesort`
- `Using temporary`

其中最该警惕的是：

- `Using filesort`
- `Using temporary`

### 4. 一个最小示例

```sql
EXPLAIN
SELECT id, title, create_time
FROM article
WHERE user_id = 1
  AND state = '已发布'
ORDER BY create_time DESC;
```

如果这条 SQL 在 `user_id`、`state`、`create_time` 上没有合理的联合索引，就很可能出现排序额外 `filesort`。

## 二、联合索引不是“拼起来就行”，它受最左匹配约束

如果有一个联合索引：

\[
\text{index}(a,b,c)
\]

它更像按 `a -> b -> c` 的顺序组织的一棵 B+ 树。

所以两个核心结论必须记住：

1. 跳过最左列，索引效果通常会大幅下降
2. 一旦中间出现范围查询，后续列的利用率会变差

## 三、B+ 树为什么能扛住大数据量

假设：

- 主键 ID 为 8 字节
- 指针为 6 字节
- InnoDB 页大小为 16KB
- 每条记录大约 1KB

那么：

- 2 层 B+ 树大约能覆盖 \(1170 \times 16 \approx 1.8\) 万行
- 3 层 B+ 树大约能覆盖 \(1170 \times 1170 \times 16 \approx 2190\) 万行

这说明当数据量从百万上到千万级以后，多一层树高就意味着多一次磁盘 I/O。

## 四、深度分页为什么慢

```sql
SELECT *
FROM article
ORDER BY id
LIMIT 1000000, 10;
```

问题不在于只取 10 条，而在于前面那 1000000 条也得先跳过。

更好的做法通常有两个：

### 1. 游标分页

```sql
SELECT *
FROM article
WHERE id > 1000000
ORDER BY id
LIMIT 10;
```

### 2. 延迟关联

先走覆盖索引查 ID，再回表查详情。

## 五、Redis 为什么快，应该怎么答才像做过项目的人

Redis 快的核心原因：

- 纯内存操作
- 单线程模型减少锁竞争和上下文切换
- I/O 多路复用支撑高并发连接

一个很直观的类比：

- 寄存器 / L1 Cache：像从口袋里拿东西
- 内存：像从书桌抽屉里拿东西
- SSD：像下楼去快递柜拿东西
- 机械硬盘：像去几公里外的集散中心拿东西

也就是说，Redis 的“快”首先是存储介质维度的优势。

## 六、缓存三剑客一定要会：穿透、击穿、雪崩

### 1. 缓存穿透

DB 和缓存里都没有，流量直接打到数据库。

常见方案：

- 布隆过滤器
- 缓存空对象

### 2. 缓存击穿

某个热点 key 过期，瞬时大量请求打到 DB。

常见方案：

- 热点 key 不设置过期
- 加互斥锁

### 3. 缓存雪崩

大量 key 同时过期，系统整体被冲垮。

常见方案：

- 过期时间加随机扰动
- 多级缓存
- 熔断降级

## 七、缓存一致性别空谈，最常用的还是 Cache Aside

这里的结论很稳：

> 更新时先更新数据库，再删除缓存。

一个最小流程：

```text
查询：先查缓存 -> 缓存未命中 -> 查数据库 -> 回填缓存
更新：先更新数据库 -> 再删除缓存
```

如果对一致性要求极高，还可以考虑“延迟双删”等增强方案。

## 八、Redis 持久化和高可用怎么理解

### 1. RDB

- 定时全量快照
- 恢复快
- 但两次快照间宕机会丢数据

### 2. AOF

- 记录写命令日志
- 数据更完整
- 文件更大，恢复更慢

### 3. 混合持久化

- RDB 负责全量
- AOF 负责增量

### 4. 高可用

- 主从复制
- 哨兵模式
- 集群模式

## 九、Docker 里的 OOM，不是把堆调大就完了

### 1. 容器隔离靠什么

- `Namespace`：隔离视图
- `Cgroups`：资源限制
- `UnionFS`：镜像分层

### 2. 为什么容器里 JVM 容易“看着没超，实际 OOM”

因为 JVM 堆大小和容器限制不是同一个概念。  
如果 JVM 没感知容器资源限制，就可能按宿主机资源估算，最后被容器直接杀掉。

比较常见的做法：

```bash
-XX:+UseContainerSupport
```

然后把 `-Xmx` 大致设为容器内存的 75% 左右，而不是把容器内存吃满。

## 十、微服务雪崩和连接池打满，排查思路要成体系

### 1. CPU 飙升怎么查

```bash
top
top -Hp <pid>
printf "%x\n" <tid>
jstack <pid>
```

也就是：

1. 先定位高 CPU 进程
2. 再定位高 CPU 线程
3. 再把线程号转 16 进制
4. 最后用 `jstack` 找到具体代码栈

### 2. 连接池满怎么查

通常先怀疑这几类问题：

- 慢 SQL
- 事务范围过大
- 事务里夹了远程耗时调用

### 3. 服务雪崩防御

- 超时控制
- 熔断降级
- 线程池隔离

## 最后

1. SQL 慢了，先看执行计划
2. 缓存异常，先判断是穿透、击穿还是雪崩
3. 容器 OOM，先确认 JVM 是否正确感知了容器限制
4. 微服务抖动，先看超时、熔断和线程池隔离
5. CPU 飙升、连接池打满，都要按“定位 -> 归因 -> 修复”顺序排查

真正成熟的后端思维，不是单独会某个工具，而是知道这些问题在系统里分别扮演什么角色。
