## 二、面试题答案

### 1. 请对比你两段实习经历，并说明每段实习的核心工作、技术难点、优化方案和收获。（方向：项目深挖）

#### 知识点讲解

项目深挖题重点不是简单介绍“我做了什么”，而是考察你是否真的参与了项目、是否理解业务目标、技术方案、难点、优化和结果。AI/Agent 岗位尤其关注你有没有把大模型、RAG、Agent、Prompt、知识库、后端服务等能力落到真实业务里。

#### 面试回答思路

先分别介绍两段实习的业务背景和你的职责，再讲每段实习的核心技术方案，接着对比难点和优化点，最后总结你的成长，比如工程能力、AI 应用落地能力、问题定位能力。

#### 标准回答答案

我会从业务目标、技术方案、难点和结果四个维度对比两段实习。第一段实习更偏业务系统开发，我主要负责后端接口、数据处理和基础业务流程，重点提升了 Python 后端、数据库设计和接口联调能力。第二段实习更偏 AI 应用或 RAG/Agent 落地，我参与了知识库构建、Query 改写、向量检索、Prompt 优化和结果评估。两者的区别是，传统业务开发更关注稳定性、接口性能和业务正确性，而 AI 应用项目除了工程稳定性，还要关注召回准确率、生成质量、幻觉控制和用户体验。我在优化上做过接口性能优化、检索策略调整、Prompt 结构优化、知识库切分和重排等工作。

#### 口语化回答答案

我一般会从“业务、技术、难点、结果”四块来说。第一段实习更像传统后端项目，主要锻炼了接口开发、数据库和业务流程。第二段更偏 AI 应用，比如 RAG、知识库、Prompt、召回这些。它们最大的区别是，后端项目主要保证功能正确和系统稳定，AI 项目还要额外考虑回答准不准、有没有幻觉、用户问得模糊时怎么处理。所以我的收获是既补了工程能力，也理解了 AI 应用怎么真正落地。

#### 可选：加分点和可能追问

### 2. 在 RAG 系统中，召回阶段常见的排序策略有哪些？长尾或语义模糊 Query 如何提升召回准确率？（方向：RAG）

#### 知识点讲解

RAG 召回阶段通常包括关键词召回、向量召回、混合召回和重排序。关键词召回适合精确词匹配，向量召回适合理解语义，混合召回能兼顾精确性和泛化能力。长尾或模糊 Query 的问题是用户表达不清，单一检索方式容易漏召或错召。

#### 面试回答思路

先说常见召回策略，再说长尾 Query 的问题，最后给出优化方法：Query 改写、意图识别、多路召回、HyDE、同义词扩展、重排和用户澄清。

#### 标准回答答案

RAG 中常见召回策略包括 BM25/ElasticSearch 关键词召回、Embedding 向量召回、关键词与向量混合召回、多路召回融合以及 Cross-Encoder 重排序。对于长尾或语义模糊 Query，可以从几个方面优化：第一，做 Query 改写，把用户口语化、模糊的表达改写成更标准的检索语句；第二，做同义词、实体、关键词扩展，提高召回覆盖率；第三，使用混合召回，避免单纯依赖向量或关键词；第四，引入 Rerank 模型，对候选文档重新排序；第五，如果用户意图不明确，可以让 Agent 先追问澄清，再检索。

#### 口语化回答答案

RAG 召回一般不会只靠一种方式，常见的是关键词召回、向量召回、混合召回，再加一个重排。长尾或者模糊问题的核心问题是“用户没说清楚”，所以我会先做 Query 改写，把问题变得更适合检索；然后做同义词扩展、多路召回，尽量别漏掉相关文档；最后用 rerank 模型把最相关的内容排到前面。如果还是不清楚，就让 Agent 追问用户。

#### 可选：加分点和可能追问

### 3. RAG 的召回排序过程一般分为几个阶段或层次？（方向：RAG）

#### 知识点讲解

RAG 检索通常不是一步完成，而是多阶段流水线。典型流程包括 Query 理解、粗召回、召回融合、重排序、上下文构造和生成。这样做是为了在效率和准确率之间平衡。

#### 面试回答思路

先讲完整流程，再强调粗召回关注覆盖率，重排关注准确率，最后说明这些阶段如何影响最终回答质量。

#### 标准回答答案

RAG 的召回排序一般可以分为四到六个层次。第一是 Query 理解，包括意图识别、关键词抽取和 Query 改写。第二是粗召回，比如 BM25、向量召回或混合召回，目标是尽量找全相关候选文档。第三是召回融合，例如 RRF，把不同召回通道的结果合并。第四是重排序，通常用 Cross-Encoder 或 rerank 模型对候选文档按相关性重新排序。第五是上下文构造，包括去重、截断、分组、控制 token 长度。最后才是大模型生成答案。这样可以兼顾召回覆盖率、排序准确率和生成质量。

#### 口语化回答答案

我理解 RAG 检索不是一步搜完就结束，一般是先理解用户问题，再做粗召回，接着融合多路结果，然后 rerank 重排，最后挑合适的上下文给大模型生成。粗召回更看重别漏，重排更看重排得准，上下文构造则决定模型能不能拿到干净、相关的信息。

#### 可选：加分点和可能追问

### 4. Query 改写有哪些方式？为什么 Query 改写能够提升召回精准度？（方向：Query 改写）

#### 知识点讲解

Query 改写是把用户原始问题转换成更适合检索系统理解的表达。用户的问题可能口语化、缺少关键词、包含歧义或上下文依赖，直接检索效果不稳定。

#### 面试回答思路

先解释 Query 改写的目的，再列方式，最后说明为什么能提高召回：补全信息、消除歧义、增强关键词、对齐知识库表达。

#### 标准回答答案

Query 改写常见方式包括：关键词抽取、同义词扩展、实体标准化、上下文补全、多 Query 生成、HyDE 假设答案生成、意图识别后改写等。它能提升召回精度的原因是，用户原始 Query 往往和知识库中的表达不一致，比如用户说“退东西”，知识库写的是“退货流程”；通过改写可以把口语表达转成标准业务术语。同时，多 Query 改写可以覆盖不同表达路径，减少漏召。对于多轮对话，还可以结合历史上下文补全省略信息，让检索语句更完整。

#### 口语化回答答案

Query 改写本质上就是把用户随口说的话，变成检索系统更容易搜到的表达。比如用户说“这个怎么退”，我们可以改写成“商品退货流程、售后退款规则”。常见方法有关键词提取、同义词扩展、实体标准化、多 Query 生成、HyDE，还有结合上下文补全。这样能让 Query 和知识库里的文本更匹配，所以召回会更准。

#### 可选：加分点和可能追问

### 5. RRF 融合中的 K 参数一般如何设置？K 变大或变小对结果有什么影响？（方向：RAG 召回融合）

#### 知识点讲解

RRF 是 Reciprocal Rank Fusion，用来融合多个召回通道的排序结果。它不直接看原始分数，而是根据排名计算融合得分，公式通常类似 `1 / (k + rank)`。

#### 面试回答思路

先解释 RRF 的作用和公式，再讲 K 的常见取值，最后分析 K 大小对头部结果和长尾结果的影响。

#### 标准回答答案

RRF 通常用于融合 BM25、向量召回等多路召回结果。它的思想是，一个文档在多个召回列表中排名越靠前，最终得分越高。常见公式是对每个召回列表计算 `1 / (k + rank)` 并求和。K 的常见经验值是 60 左右，但实际要根据数据集调参。K 越小，排名靠前的结果权重越大，头部结果影响更强，但可能对某一路召回过于敏感。K 越大，不同排名之间的差距会被平滑，融合结果更稳定，但头部强相关结果的优势会被削弱。

#### 口语化回答答案

RRF 是用来融合多路召回的，比如关键词召回和向量召回。它不太关心原始分数，而是看每个文档在各个列表里的排名。K 一般可以从 60 这种经验值开始调。K 小的时候，排前面的文档优势特别明显；K 大的时候，排名差距会被拉平，结果更稳，但可能没那么突出头部强相关文档。

#### 可选：加分点和可能追问

### 6. 项目中遇到召回不准时，你们做了哪些优化？具体怎么做？（方向：项目深挖）

#### 知识点讲解

召回不准可能来自多个环节：数据质量差、文档切分不合理、Embedding 模型不适配、Query 表达不清、召回策略单一、缺少重排、知识库未更新等。

#### 面试回答思路

先承认召回不准是常见问题，再按排查路径回答：数据、切分、检索、重排、评测。最好结合具体指标，如 Recall@K、MRR、人工标注集。

#### 标准回答答案

项目中召回不准时，我会先定位问题来源。第一看数据质量，检查知识库是否有重复、过期、缺失内容。第二看切分策略，比如 chunk 太大导致噪声多，太小导致上下文不完整，可以调整 chunk size 和 overlap。第三优化 Query，比如做关键词抽取、同义词扩展和 Query 改写。第四使用混合召回，把 BM25 和向量召回结合起来。第五加入 rerank 模型，提高候选文档排序准确率。最后建立评测集，用 Recall@K、Top1 命中率、人工相关性评分来验证优化效果。

#### 口语化回答答案

我会先判断到底是哪一层出问题。比如知识库内容是不是脏，文档切分是不是太碎或太长，Embedding 模型是不是不适合业务，Query 有没有表达不清。优化上我会做数据清洗、调整切分策略、Query 改写、BM25 加向量的混合召回，再加 rerank。最后一定要用评测集看效果，不然只是感觉变好了。

#### 可选：加分点和可能追问

### 7. 用户输入非常模糊时，实际工程中应该如何处理？（方向：Agent 架构）

#### 知识点讲解

模糊输入是 Agent 系统常见问题。系统不能直接胡乱回答，而应该判断意图是否明确、信息是否足够，再决定是检索、追问、推荐选项还是给出保守回答。

#### 面试回答思路

先说明不能直接生成答案，再讲处理流程：意图识别、槽位检查、上下文补全、澄清追问、候选推荐、兜底策略。

#### 标准回答答案

面对非常模糊的输入，我会设计一套意图识别和信息补全机制。首先判断用户意图是否明确，如果能结合上下文补全，就用历史对话补全 Query；如果不能补全，就抽取必要槽位，比如商品、订单、问题类型等。缺少关键槽位时，Agent 不直接回答，而是向用户发起澄清问题。对于可能的多个意图，可以提供选项让用户选择。工程上还可以设置置信度阈值，低于阈值时进入追问或人工兜底流程，避免模型幻觉。

#### 口语化回答答案

如果用户说得很模糊，我不会让模型直接猜。一般会先判断他大概想干什么，再看关键信息够不够。能从上下文补的就补上，补不上就追问，比如“你是想问退货、物流还是商品参数？”如果有多个可能意图，也可以给用户几个选项。核心是别硬答，先把问题问清楚。

#### 可选：加分点和可能追问

### 8. 面对一次性说不清需求的用户，Agent 应该如何提示、追问和解决问题？（方向：Agent 交互设计）

#### 知识点讲解

Agent 不只是问答机器人，还需要具备多轮对话、任务拆解、状态管理和工具调用能力。用户说不清时，Agent 要通过对话把任务逐步明确。

#### 面试回答思路

先讲 Agent 的多轮任务处理流程，再讲追问策略，最后说明如何进入执行和反馈闭环。

#### 标准回答答案

面对一次说不清需求的用户，Agent 可以采用“理解意图、拆解任务、澄清信息、执行反馈”的流程。首先用意图识别判断用户大方向，比如咨询、办理、投诉。然后根据任务模板检查必要信息是否完整，例如商品、订单、时间、问题类型。缺少信息时，Agent 应该一次只问一到两个关键问题，避免让用户负担太重。信息完整后，再调用知识库、数据库或业务 API 执行任务。最后把处理结果反馈给用户，并确认是否解决问题。这样可以提高任务完成率，也能减少模型乱猜。

#### 口语化回答答案

我会把 Agent 设计成一个会“引导”的助手。用户说不清时，它先判断大概是哪类问题，再看还缺什么信息。比如客服场景里，可能缺订单号、商品名、问题类型。Agent 不应该一次问一堆，而是按优先级追问关键问题。信息齐了以后再查知识库或调用接口，最后确认用户的问题有没有解决。

#### 可选：加分点和可能追问

### 9. 如何从数据、检索和生成三个方面降低 RAG/Agent 系统幻觉？（方向：RAG 幻觉治理）

#### 知识点讲解

幻觉通常来自知识库数据错误、检索不到正确内容、上下文噪声太多或模型生成时脱离依据。治理幻觉要从数据源到检索再到生成全链路控制。

#### 面试回答思路

按数据、检索、生成三层回答，每层给具体措施，最后补充评测和监控。

#### 标准回答答案

从数据层看，要保证知识库内容准确、及时、结构清晰，做去重、清洗、版本管理和权限控制。从检索层看，要优化文档切分、Embedding 模型、混合召回、Query 改写和 rerank，确保模型拿到的是相关且高质量的上下文。从生成层看，要在 Prompt 中要求模型基于检索内容回答，不能编造；对低置信度问题可以拒答或追问；同时可以要求引用来源、做答案校验。上线后还需要建立评测集和人工反馈机制，持续监控命中率、拒答率、用户满意度和幻觉案例。

#### 口语化回答答案

我会从三层控制。第一是数据别脏，知识库要准、要新、要去重。第二是检索要准，不能把不相关的内容塞给模型，所以要做好切分、混合召回、Query 改写和 rerank。第三是生成要约束，Prompt 里要求只能基于材料回答，不确定就说不知道或者追问。最后还要靠评测集和线上反馈持续发现幻觉。

#### 可选：加分点和可能追问

### 10. Agent 项目如何设计评测方案？（方向：Agent 评测）

#### 知识点讲解

Agent 评测不能只看回答对不对，还要看任务是否完成、工具是否调用正确、多轮对话是否稳定、成本和延迟是否可接受。

#### 面试回答思路

先说明评测维度，再讲数据集构建，然后讲自动评测、人工评测和线上指标。

#### 标准回答答案

Agent 项目的评测可以分为离线评测和线上评测。离线评测先构建覆盖不同意图、难度和异常情况的数据集，评估意图识别准确率、任务完成率、工具调用准确率、回答正确性、幻觉率和安全性。对于多轮任务，还要评估追问是否合理、状态是否保持一致。线上评测关注用户满意度、一次解决率、转人工率、平均响应时间、调用成本和失败率。复杂场景可以结合人工打分和 LLM-as-Judge，但关键业务结果最好用规则或真实业务指标校验。

#### 口语化回答答案

Agent 评测不能只看回答像不像，还要看它有没有把事情办成。我会先做一批离线测试集，覆盖不同意图和异常情况，看意图识别、工具调用、任务完成、幻觉率这些指标。上线后再看一次解决率、转人工率、用户满意度、延迟和成本。对于复杂回答可以用人工加模型评审，但业务结果最好用真实数据验证。

#### 可选：加分点和可能追问

### 11. 后端压测和性能优化时，如何定位问题？（方向：Python 后端）

#### 知识点讲解

压测定位问题要看系统瓶颈在 CPU、内存、数据库、缓存、网络、外部 API 还是模型推理。AI 应用还要关注大模型调用延迟、向量检索耗时和并发下的资源占用。

#### 面试回答思路

先讲压测指标，再讲定位链路，最后讲常见优化手段。

#### 标准回答答案

后端压测时，我会先关注 QPS、响应时间、P95/P99 延迟、错误率、CPU、内存、数据库连接数和接口吞吐。定位问题时先用压测工具复现瓶颈，再通过日志、链路追踪和监控拆分每个阶段耗时，比如参数校验、数据库查询、缓存访问、向量检索、模型调用等。如果瓶颈在数据库，可以优化索引、SQL 和连接池；如果在模型调用，可以做异步、流式返回、缓存、限流或并发控制；如果在接口层，可以优化代码逻辑、减少重复计算、增加缓存和队列削峰。

#### 口语化回答答案

我会先看压测指标，比如 QPS、平均耗时、P95、错误率和资源占用。然后把一次请求拆开，看时间花在哪：数据库、缓存、向量检索、模型接口还是业务代码。定位到瓶颈后再针对优化，比如 SQL 慢就看索引和连接池，模型慢就做缓存、异步、流式输出或限流。核心是先量化，再定位，最后优化。

### 12. 如何设计一个电商客服 Agent 的完整评测体系？（方向：AI 应用落地场景题）

#### 知识点讲解

电商客服 Agent 评测要覆盖商品咨询、售后咨询和投诉安抚三类任务。不同任务的评价重点不同：商品咨询看准确性，售后看流程合规，投诉安抚看情绪处理和问题解决。

#### 面试回答思路

先拆任务类型，再设计离线数据集和指标，最后讲线上指标与满意度衡量。

#### 标准回答答案

我会把电商客服 Agent 的评测分为三类场景。商品咨询重点评估商品信息准确率、推荐相关性和知识库引用正确性；售后咨询重点评估流程合规性、订单/退款状态判断准确率和工具调用正确率；投诉安抚重点评估情绪识别、安抚话术、升级人工时机和用户问题解决率。数据集上要覆盖正常问题、模糊问题、极端情绪、多轮对话和边界场景。线上指标可以看一次解决率、转人工率、重复咨询率、平均处理时长、用户满意度、差评率和投诉升级率。满意度难直接衡量时，可以用情绪变化、是否继续追问、是否重复投诉等间接指标。

#### 口语化回答答案

我会先按三类任务拆：商品咨询、售后、投诉。商品咨询看答得准不准，售后看流程对不对、工具调得对不对，投诉场景要看情绪识别和安抚效果。数据集要覆盖正常问题、模糊问题、多轮问题和情绪激烈问题。上线后看一次解决率、转人工率、重复咨询率、处理时长、满意度和投诉升级率。满意度不好直接量化，就用情绪变化、是否重复投诉这些指标辅助判断。

### 13. 只有 500 条真实标注样本，却要覆盖 200 多种 Text-to-SQL 查询模式，如何设计训练集构建流程？（方向：Text-to-SQL 数据构建）

#### 知识点讲解

Text-to-SQL 数据构建的核心是覆盖查询模式、保证 SQL 正确性和自然语言多样性。样本少时，需要用模板、规则、LLM 合成和执行校验来扩充数据。

#### 面试回答思路

先讲真实样本分析，再讲合成策略、质量控制和迭代优化。

#### 标准回答答案

我会先分析 500 条真实样本，抽象出 schema、业务意图和 SQL 查询模式，比如单表查询、多表 join、聚合、排序、分组、条件过滤、嵌套查询等。然后为 200 多种查询模式设计模板，每种模式生成多种自然语言表达，并结合 LLM 做语义改写和数据增强。质量控制上，SQL 必须经过语法校验和数据库执行校验，结果异常的样本要过滤；同时抽样人工审核，保证自然语言和 SQL 语义一致。迭代时可以根据模型错误案例补充难例，比如 join 错误、字段混淆、聚合条件遗漏等，逐步提升覆盖率和准确率。

#### 口语化回答答案

我会先把 500 条真实样本拆开看，抽出有哪些表、字段和查询模式。然后按 200 多种模式做模板，比如单表、多表 join、聚合、排序、分组这些，再用大模型生成不同问法。生成完不能直接用，要跑 SQL 语法校验和真实执行，看结果是否合理，还要人工抽检。后面根据模型错在哪，继续补难例，比如字段混淆、join 条件错、聚合漏条件这些。
